摘要与结论#

先看这一页：可行、值得做，但边界必须先画清楚。

这个产品不是“又一个 B 站下载器”，而是以本地素材库为中心的个人工作流：从收藏夹/稍后再看/UP 主投稿中拉取列表， 本地勾选需要同步的条目，下载后进入可标签化、可搜索、可播放的媒体库。它与 Eagle 的相似点是“收集 → 整理 → 检索 → 预览”的心智模型， 区别是素材源自动来自 B 站，并且保留来源、UP、分区、弹幕、字幕等上下文。

✓
结论：建议立项，但采用“薄下载、厚管理”的策略。

下载/解析交给 yt-dlp + FFmpeg，不自研签名、不碰风控、不绕过付费内容； 自研部分集中在列表选择、任务编排、SQLite 素材库、标签/智能收藏夹、Artplayer 播放与弹幕。这样技术风险最低，差异化最高。

◎
Why now

为什么现在做

2026 年 B 站维权升级，多个头部下载器与 API 文档项目归档/关停；同时活跃项目证明“登录态 + 选择性同步 + 本地媒体库”仍有真实需求。窗口存在，但必须低调、克制、个人化。

◈
Product gap

差异化在哪里

现有工具要么是下载 CLI，要么是 NAS/Emby 同步器，要么是通用素材管理器。没有一个把“B 站选择性同步 + Eagle 式标签/预览 + 内置弹幕播放”做成一体。

01

背景与目标#

先把“为什么要做”说清楚，避免做成一个功能堆砌的下载器。

1.1 问题陈述

B 站收藏夹是一个典型的“收藏即吃灰”场景：收藏动作很轻，但后续的检索、回看、二次使用很重。平台侧的收藏夹以时间流和文件夹为主， 不适合按项目、主题、素材用途来组织；视频也可能因为下架、删除、版权变更而失效。对创作者、研究者、剪辑/设计从业者来说， 真正需要的是一个本地可掌控、可标签化、可快速预览的素材库，而不是又一个在线列表。

⌕

找不回来

收藏夹只有标题/UP/时间，缺少“我为什么收藏它”的上下文；跨收藏夹、跨 UP 的检索能力弱。

◷

会失效

下架、删除、分区调整都会让在线内容消失；本地备份是唯一可控的长期保存方式。

▤

不能当素材用

平台播放器不是素材管理器：没有标签、评分、备注、批量整理、封面/字幕/弹幕的素材级管理。

1.2 产品定义

BiliShelf（暂定名）是一个 Windows 本地、单用户、离线优先的 B 站素材管理工具： 先拉取收藏夹/稍后再看/UP 主投稿的“清单”，由用户本地勾选要同步的条目，下载后进入一个类似 Eagle 的素材库， 支持标签、文件夹、智能收藏夹、搜索、内置播放、弹幕/字幕、批量操作，并可选生成 Emby/Jellyfin 兼容的 NFO。

i
关键词：选择性同步

不是“把整个收藏夹无脑镜像到本地”。第一优先级是先拿到列表和元数据，让用户看到时长、UP、分区、是否已下载、预计体积， 再决定同步哪些。这既符合素材库的使用方式，也能显著降低带宽、存储与风控压力。

1.3 典型用户故事

角色场景期望动作价值
视频创作者 收藏了大量参考片、教程、访谈，需要按项目找素材 按“项目/主题”建文件夹和标签；搜索标题、UP、备注；悬停预览；双击播放并定位片段 把“收藏”变成可复用的素材库
设计师 / 剪辑师 需要管理封面、字幕、音频、短视频片段 多选批量打标签、评分、重命名；导出文件；按颜色/格式/时长筛选 接近 Eagle 的素材管理体验
研究者 / 学生 课程、讲座、纪录片需要长期保存与笔记 选择性同步；字幕检索；时间戳笔记；离线播放 可检索的本地知识库
普通用户 收藏夹里有很多“以后再看”，但不想全部下载 先看清单；按未下载/时长/UP 过滤；只同步感兴趣的部分 低负担的收藏夹整理

1.4 目标与非目标

目标（v1）

  • Windows 10/11 桌面，单机单用户，安装即用
  • 收藏夹 + 稍后再看 + UP 主投稿/合集/分P 的列表拉取
  • 先拉列表、本地勾选、再下载的选择性同步
  • 标签、文件夹、智能收藏夹、全文搜索、批量操作
  • 内置播放器：弹幕、字幕、倍速、截图、片段笔记
  • 封面、缩略图、字幕、弹幕、NFO 等素材级管理
  • 任务可暂停/恢复/重试，崩溃后不丢队列

非目标（v1 明确不做）

  • 不做多用户、云同步、在线分享、社区
  • 不做付费课程/充电专属/大会员内容的绕过
  • 不做 DRM 破解、签名逆向、风控绕过、批量爬取
  • 不做直播录制、评论抓取、动态/专栏全量归档
  • 不做 macOS/Linux/NAS/Docker（架构预留，不实现）
  • 不做插件市场、AI 视觉搜索（后续再评估）
  • 不与平台播放器/推荐流竞争，只服务本地素材工作流

2.4 关键发现

Finding 01

下载能力已经商品化

yt-dlp / yutto / BBDown（曾）都能处理 B 站格式选择、分片、合并、字幕。自研下载器是重复劳动，且要持续对抗接口变化。正确做法是把下载引擎做成可替换的 sidecar。

Finding 02

“同步”与“整理”是断层

bili-sync 解决了自动同步到媒体库，但整理体验交给 Emby/Jellyfin；Eagle/Billfish 解决了整理，但不知道 B 站收藏夹。中间的选择性同步 + 素材级管理是空白。

Finding 03

本地播放与弹幕已经可组合

Artplayer 原生支持 ASS/SRT/VTT，并有弹幕、JASSUB、章节、VTT 缩略图插件；Danmaku.js 可做 Canvas 高性能渲染。无需自研播放器内核。

Finding 04

2026 年的合规环境已变

B 站对“非公开接口收集/传播、绕过登录态与会员体系”采取法律行动，多个头部项目归档。新产品必须默认“个人、本地、克制”，并把合规写进产品约束，而不是免责声明。

3.2 差异化定位

01

以“清单”为入口

打开应用先看到来源清单，而不是下载按钮。用户像整理邮件一样处理收藏：未下载、已下载、已失效、待看、喜欢的。

02

以“素材”为最小单位

视频不是唯一对象：封面、字幕、弹幕、音频、预览片段、NFO 都是 asset，可单独替换/导出/重建。

03

以“本地可控”为底线

SQLite + 文件 sidecar；库目录可整体复制；数据库丢了可从 sidecar 重建；不依赖云服务。

3.3 目标用户旅程

登录

内嵌 B 站登录页，用户手动扫码/登录；只保存加密后的 Cookie，不保存密码。

发现来源

自动读取收藏夹列表与稍后再看；UP 主投稿/合集通过 URL 添加；显示数量与最近同步时间。

拉清单

只请求列表与元数据，不下载；展示标题、UP、时长、分区、是否已下载、预计体积、失效状态。

本地筛选

按时长、UP、分区、收藏时间、未下载、已失效过滤；勾选需要的条目；支持“全选本页”。

加入队列

选择画质/编码策略；检查磁盘空间；任务进入队列，可暂停、重试、调整并发。

下载与后处理

下载视频/音频并合并；抓取封面、字幕、弹幕；生成缩略图/预览；写入 sidecar 与数据库。

整理

自动打来源/UP/分区标签；用户补充项目标签、评分、备注；放入文件夹或智能收藏夹。

检索与回看

全文搜索、标签筛选、悬停预览、空格快速预览、双击播放；记录播放进度与最近观看。

导出/兼容

复制文件、导出 CSV/JSON、可选生成 NFO/海报；需要时交给 Emby/Jellyfin 或 Eagle。

3.4 不做什么：避免产品失焦

  • 不做“万能下载器”：不做非 B 站站点、不做直播录制、不做评论/动态归档。范围越窄，合规与维护成本越低。
  • 不做在线社区：不做分享、点赞、排行榜、云端素材库；本地单用户是产品约束，不是临时限制。
  • 不做“自动追更所有 UP”：v1 只做用户明确添加的来源；自动追更会放大请求量与合规风险。
  • 不做“最高画质强制”：只提供账号本身可访问的画质；不绕过会员/付费/地区限制。

  • Cookie：Windows DPAPI（Electron safeStorage）加密；不写日志
  • 列表请求：全局 1 req/s，随机 0.3–0.8s 抖动
  • 下载并发：默认 2，最大 3；分片并发默认 1–2
  • 风控命中：立即停止队列，冷却 30 分钟，提示用户

  • 默认 1080P AVC + AAC，兼容优先

  • 付费/充电/课程：不提供绕过；无权限则跳过
  • 字幕/弹幕：只抓取该视频公开可用的数据

4.3 技术性合规要求

  • 速率限制：列表接口与下载共用令牌桶；任务队列串行化；失败指数退避；禁止“无限重试”。
  • 请求最小化：只请求列表、详情、播放地址、字幕、弹幕、封面所需字段；不拉取无关数据。
  • 不固化接口：所有平台交互封装在 SourceAdapter / DownloadEngine 接口后；接口变化时只改适配器。
  • 可关闭：提供“暂停所有网络请求”“仅播放本地”“清除登录态”开关；这是产品功能，不是隐藏设置。
  • 可审计：本地日志记录任务状态与错误码，但不记录 Cookie、完整播放地址、签名参数。

4.5 结论

合规不是“加一条免责声明”就能解决，而是产品边界：只处理用户自己可见、可播放的内容；只做本地个人使用；不绕过任何访问控制；不公开传播。 在这个边界内，工具的技术价值成立；越过边界，风险会迅速超过收益。建议在设置页放一个“使用边界”说明，并在首次启动时让用户确认。

05

技术方案与架构#

Electron 外壳 + 本地服务 + 可替换下载引擎 + 本地素材库。

5.1 设计原则

Principle 01

下载是外设，不是核心

把 yt-dlp / FFmpeg 当作可替换的 sidecar；应用只负责参数、进度、重试、后处理与入库。引擎坏了可以换，素材库不能坏。

Principle 02

数据库是索引，不是唯一真相

每个条目有 sidecar metadata.json；SQLite 可重建。这样库目录可搬迁、可备份、可被其他工具读取。

Principle 03

主进程可信，渲染进程沙箱

所有文件系统、Cookie、子进程、数据库访问都在主进程；渲染进程只通过白名单 IPC 调用，禁用 Node 集成。

Principle 04

本地优先，网络可断

列表同步、下载是可选在线动作；浏览、搜索、播放、标签、导出必须完全离线可用。

5.6 失败处理原则

  • 下载失败：任务保留，指数退避重试 3 次；区分网络、风控、权限、磁盘、解析失败；可手动重试/跳过。

  • 进程崩溃：启动时扫描 *.part 与 job 表，恢复为 paused；用户确认后继续。
  • 数据库损坏：WAL + 定期备份；提供“从库目录扫描重建”；sidecar 是兜底。
  • 文件被移动/删除：播放/缩略图失败时标记 missing，提供重新定位/重新下载。

6.5 索引与重建

  • 唯一键：videos(bvid, cid) 唯一；assets(video_id, type) 唯一；文件哈希用于发现重复。
  • WAL：PRAGMA journal_mode=WAL、synchronous=NORMAL；写入批量事务；避免长事务。
  • 迁移：Drizzle/Kysely migration；启动时检查 schema 版本；失败时备份 DB 并进入只读模式。
  • 重建：扫描 media/**/metadata.json → 校验文件存在 → 重新 ffprobe（可选）→ 重建 videos/assets/tags；标签从 sidecar 恢复。

7.4 下载任务状态机

queued→ resolving→ downloading→ postprocessing→ done failed paused canceled
queued → resolving

解析视频/分P/可用格式；失败进入 failed，可重试。

downloading

spawn yt-dlp；解析进度；支持暂停/取消；网络错误退避。

postprocessing

ffprobe 校验、缩略图、字幕/弹幕、sidecar、NFO、入库。

  • 幂等：同一 bvid + cid 同时只允许一个活跃 job；重复入队返回已有 job。
  • 持久化：状态写入 download_jobs；启动时把 downloading 重置为 paused，由用户恢复。
  • 取消：Windows 下终止进程树（taskkill /T /F 或等效库）；清理 .part 与临时目录。
  • 重试：最多 3 次；网络/5xx/超时指数退避；权限/404/风控不自动重试，提示用户。
  • 优先级：用户手动置顶；默认按加入顺序 FIFO；同来源可批量调整。

7.9 限速、重试与错误码

限速策略

  • 列表：全局 1 req/s；页间 0.3–0.8s 随机抖动

  • 风控：暂停全局 30 分钟；不自动切换 IP/账号
  • 夜间模式：可设置 23:00–07:00 限速/暂停

错误分类

  • NETWORK：超时/断网/DNS → 自动重试

  • FORBIDDEN：无权限/付费/地区 → 跳过，提示
  • NOT_FOUND：失效/删除 → 标记 unavailable
  • DISK：空间不足/写入失败 → 暂停队列
  • PARSE：格式/解析失败 → 保留日志，提示升级引擎
  • FFMPEG：合并/转码失败 → 保留原始分片，允许重试

9.2 本地文件流：自定义协议

不要直接用 file://。Electron 官方安全建议是使用自定义协议，并把它限制在库目录内。 注册 bilishelf:// 为 standard/secure/stream/supportFetchAPI，然后在主进程处理 Range 请求。

Electron 主进程：bilishelf:// 协议（概念代码）
import { protocol, net } from 'electron';
import fs from 'node:fs';
import path from 'node:path';
import { Readable } from 'node:stream';

protocol.registerSchemesAsPrivileged([{
  scheme: 'bilishelf',
  privileges: { standard: true, secure: true, supportFetchAPI: true, stream: true }
}]);

app.whenReady().then(() => {
  protocol.handle('bilishelf', async (req) => {
    // 只允许 media 主机；id 映射到 DB 中的绝对路径，禁止路径穿越
    const u = new URL(req.url);
    if (u.hostname !== 'media') return new Response('not found', { status: 404 });

    const filePath = resolveLibraryFile(u.pathname); // 必须在库根目录内
    const stat = await fs.promises.stat(filePath);
    const range = req.headers.get('range');
    const type = mimeFromExt(filePath);

    if (!range) {
      return new Response(Readable.toWeb(fs.createReadStream(filePath)), {
        headers: { 'content-type': type, 'accept-ranges': 'bytes', 'content-length': String(stat.size) }
      });
    }

    const [startStr, endStr] = range.replace(/bytes=/, '').split('-');
    const start = Number(startStr);
    const end = endStr ? Number(endStr) : Math.min(start + 4 * 1024 * 1024 - 1, stat.size - 1);
    const stream = fs.createReadStream(filePath, { start, end });

    return new Response(Readable.toWeb(stream), {
      status: 206,
      headers: {
        'content-type': type,
        'accept-ranges': 'bytes',
        'content-range': `bytes ${start}-${end}/${stat.size}`,
        'content-length': String(end - start + 1)
      }
    });
  });
});
△
安全要点

路径必须由数据库 ID 映射，不能直接拼接用户输入；解析后校验 realpath 仍在库根目录内；只允许 GET/HEAD； 对 ..、符号链接、UNC 路径、ADS 流保持警惕。渲染进程永远拿不到真实绝对路径（可只暴露相对 ID）。

9.3 弹幕：解析与渲染

B 站弹幕 XML 的核心是 <d p="时间,模式,字号,颜色,时间戳,池,用户,行号">文本</d>。 模式 1–3 为滚动，4 为底部，5 为顶部。把 XML 转成 Danmaku.js 的 comments 即可。

弹幕解析（TypeScript 概念）
type DanmakuComment = {
  text: string;
  time: number;
  mode: 'rtl' | 'top' | 'bottom';
  style: { fontSize: string; color: string; textShadow: string };
};

function parseBilibiliDanmaku(xml: string): DanmakuComment[] {
  const doc = new DOMParser().parseFromString(xml, 'text/xml');
  return [...doc.querySelectorAll('d')].map(d => {
    const [time, mode, size, color] = (d.getAttribute('p') ?? '').split(',');
    const c = Number(color) || 0xffffff;
    return {
      text: d.textContent ?? '',
      time: Number(time) || 0,
      mode: mode === '4' ? 'bottom' : mode === '5' ? 'top' : 'rtl',
      style: {
        fontSize: `${Number(size) || 25}px`,
        color: `#${c.toString(16).padStart(6, '0')}`,
        textShadow: '-1px -1px #000, -1px 1px #000, 1px -1px #000, 1px 1px #000'
      }
    };
  }).filter(x => x.text.trim());
}

Day 6：UI 骨架

15.4 附录：文件命名与 Windows 路径规则

  • 模板：{year}/{upName}/{bvid}_{cid}/{title}；用户可改为“平铺/按收藏夹/按项目”。
  • 清洗：移除 < > : " / \ | ? * 与控制字符；合并空白；去掉结尾空格/句点。
  • 保留名：CON, PRN, AUX, NUL, COM1-9, LPT1-9 加前缀下划线。
  • 长度：单段 ≤ 80 字符；完整路径尽量 ≤ 240 字符；超长时截断标题并加 6 位哈希。
  • 冲突：大小写不敏感比较；同名加 _a1b2c3。
  • Unicode：统一 NFC；保留中文；避免 emoji 作为唯一可区分字符。
  • 多P：P01 前缀或子目录；NFO 开启时映射为 season/episode。
